# Syndemics Lab R Style Guide

The motivation for the Syndemics Lab R Style Guide is public deployment and open contribution to our code. We intend to distribute and utilize open source software and this style guide is the standard for R syntax in our repositories. We hope this style guide makes contribution to our projects easy. This guide is heavily based off the [Tidyverse Style Guide](https://style.tidyverse.org/) with a handful of modifications per the Syndemics Lab developers' preferences. All pull request workflow CI/CD checks require passing the style check before approval. Note: this guide primarily applies to R scripts and packages. Notebook repositories and Rmd/qmd notebooks follow the notebook styleguide.

## R Styling Packages

Our repositories are (like tidyverse) supported by [styler](https://styler.r-lib.org/) and [lintr](https://github.com/r-lib/lintr). We have a few additional changes that we add to the default lintr file for customization and operability between our language guides.

## R Scripts

Frankly, if you're writing an R Script I'd recommend taking a look at Rmd and qmd notebooks. R scripts should only be used as a last resort as they tend to want very strict data structures and lend thesmelves to bad documentation and difficult readability. If you can't write it as a functional programming package, use a notebook. If you can't use a notebook, try breaking down what you're doing into more bite-size pieces and turn those into functions. Again, ONLY use R scripts (non-functional) as a complete last resort **and** you are completely confident in explaining exactly what you did 10 years down the road.

## Packages

The remainder of this style guide focuses on writing R code with the idea of deploying packages. Packages are the building block for all modern programming langauges. If you use CRAN, you've used a package. Traditionally, packages are invoked through the `library()` function call when you need to use them.

 **NOTE: This is NOT the style guide for R-Markdown and Quarto Notebooks!**

## Repo Structure

Outlined below is the base requirement for Syndemics package repositories. It follows the [posit cheatsheet](https://rstudio.github.io/cheatsheets/html/package-development.html). This is a non-exhaustive list of required files/folders, but instead a minimum viable product.

- `R/` - Where the R code goes
- `DESCRIPTION` - The Metadata file, follows from [r-pkg documentation](https://r-pkgs.org/description.html)
- `NAMESPACE` - Generally controlled by Roxygen2
- `tests/` - Testing functionality to verify accuracy of code
- `man/` - CLI Documentation generated by Roxygen2
- `vignettes/` - GUI Documentation generated by Roxygen2
- `data/` - Any associated data
- `.gitignore` - The file used to ignore details within git
- `README.md` - The base file used to describe the contents of the file
- `LICENSE.md` - The Syndemics specific open source license
- `.lintr.R` - The lintr adjustments for Syndemics style
- `projectname.Rproj` - The project file that is generally associated with RStudio

## File Naming

There are a few standards we really want to stick to. They are:

1. All file names should ONLY contain lowercase letters (except the single `.R` in the extension).
2. If you have more than one word in your title, use underscores instead of spaces.
3. File names should always be human readable.
4. File names should always avoid using numbers or special characters.
5. If a file contains a single function, the file name is the same name as the function.
6. The only extension should be `.R`.

```text
# Good Examples
my_somewhat_long_filename.R
exploratory_data_analysis.R
calculate_heatmap.R

# Bad Examples
no spaces please.R
CamelCaseIsWrongToo.R
capitalize_the_extension.r
no_dates_please_071025.R
never_tempt_fate_FINAL.R
```

## File Organization

Each R file should be able to be broken up into 3 sections:

1. File Header
2. Public Functions
3. Private Functions

All functions should make use of [Roxygen2](https://github.com/r-lib/roxygen2) for documentation, library imports, and exporting.

### File Header

The file header should follow the pattern:

```r
################################################################################
## File: <filename>                                                           ##
## Project: <project name>                                                    ##
## Created Date: <dd MMM yyyy>                                                ##
## Author: <author name>                                                      ##
## -----                                                                      ##
## Last Modified: <date>                                                      ##
## Modified By: <author name>                                                 ##
## -----                                                                      ##
## Copyright (c) <yyyy> Syndemics Lab at Boston Medical Center                ##
################################################################################
```

### Public Functions

All functions should have Roxygen2 documentation above them. This is the preferred way to document functions as it clearly and visibly separates the documentation apart to each function. If, instead, you decide to document all public functions in the same shared documentation header, all documented functions should immediately follow the documentation header as shown below:

```r
#' A lot of functions are documented here
#'
#' ...documentation for functions using `describeIn`...
#' @name shared-documentation
NULL

#' @describeIn shared-documentation get mean
#' @export
get_mean <- function(x) {
    # ...
}

#' @describeIn shared-documentation get sum
#' @export
get_sum <- function(x) {
    # ...
}
```

## Documentation

Documentation is crucial to any good code. As mentioned earlier, we document code via the [Roxygen2](https://github.com/r-lib/roxygen2) package.

### Documentation Tags

There are a lot of documentation tags used in Roxygen. We allow the majority of them in our style guide as necessary. However, we always require the `@importFrom`, `@param`, `@export`, and `@noRd` tags when applicable as they are required to build, import, and make packages function correctly. However, additional Roxygen2 tags include:

- `@title`
- `@description`
- `@reference`
- `@examples`
- `@section`
- `@seealso`
- etc.

### Function Documentation Outline

Function documentation blocks have a standard pattern. For starters, all lines in the block start with the symbol `#'`. Afterwards, the pattern follows:

1. Title
2. Description
3. Additional details: references, examples, related functions, etc.
4. Explicit Imports
5. Parameters
6. Export or NoRd

For example:

```r
#' An example of a good function document title
#'
#' @description
#' The description of the good function goes here. If you are multiple lines 
#' long then you must use the description tag. If a single line it is not 
#' required. Worth mentioning here is the expected return value.
#'
#' @importFrom dplyr select mutate filter
#' @param parameter The description of the parameter value.
#' @param new_parameter The description of the new_parameter value.
#' @export
good_function <- function(parameter, new_parameter){
    #...
}
```

This pattern is required for Roxygen to recognize and build the `NAMESPACE` correctly.

### Importing Libraries and Functions

Imports in packages are controlled via the `DESCRIPTION` file. Users should add their imports accordingly and use them with the package prefix (`::`). If you do not want to apply the package prefix you must utilize the `@importFrom` tag and specify the specific function to import. You should never attempt to import the full package through Roxygen as it can create dependency conflicts across the entire package.

We also allow package import files in the `R/` directory. If so desired, users must place all `@importFrom` tags in a file titled `{packagename}-package.R` following the [Roxygen2 Namespace guide](https://roxygen2.r-lib.org/articles/namespace.html).

### Exporting and No Rd

If we want users to call our functions, we must apply the `@export` tag. This tells Roxygen to add this function to the `NAMESPACE` and it becomes accessible to users that install the package. If you want to create a function that is internal to the package (i.e. it is not for public use) we need to ensure no Rd files are generated. This is done with the tag `@noRd` instead of export. One of these tags MUST be used for each function to clearly explain the purpose intended and the expected results/uses.

## Code Syntax

As mentioned above, most of our code syntax follows the tidyverse standard. However, in an effort to conform with other language standards across the lab we have a few unique details.

### Indentation

The first, and perhaps most prominent difference is we utilize 4-space indentation rather than the traditional 2-space indentation. This is because Python and C++ standards both advice 4 spaces.

### Function and Variable Naming

No functions nor variables should EVER use the `.` in their name. The `.` is used by Object Oriented Languages to denote object ownership and thus transitioning between languages makes it incredibly difficult to parse. Instead, use the standard underscore, `_`. This is referred to as "snake case."

```r
# Good
my_function <- function(x) # No dots
get_addition <- function(x_1, x_2) # Even in variables

# Bad
my.function <- function(x) # Please don't use dots
get_addition <- function(x.1, x.2) # It gives software engineers nightmares
```

We recognize this is commonplace in R, but as a lab using multiple languages, we should avoid it.

### Return Types

ALWAYS used explicit returns. DO NOT rely on R's implicit return functionality. This means all functions should end with the `return()` call.

### .lintr.R example

Below is the default linters we change as part of the style guide. More can be added, but this is the minimum. We must turn off the line length, indentation, and return checks.

```r
linters <- lintr::linters_with_defaults(
    indentation_linter = NULL,
    return_linter = NULL,
    line_length_linter = NULL
)
```
